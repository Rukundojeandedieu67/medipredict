## Implementation status

### `backend/`

Implemented: FastAPI application, permissive-configurable CORS, settings via environment variables, SQLAlchemy models and SQLite configuration, CSV loading, model inference, health/summary/risk-register/upload/transfer/trust-metric routes, and Pydantic response schemas. Database tables are created at startup.

Incomplete: request handlers do not persist uploaded data or read inventory from the database; the CSV is the live data store. No authentication, authorization, migrations, or operational monitoring are present. `get_db` and several ORM imports/dependencies are unused by the routes.

### `ml_engine/`

Implemented: RandomForest training pipeline, one-hot categorical preprocessing, persisted model/encoder and metrics artifact, and API inference fallback based on days of stock cover.

Incomplete/unsafe: the training target `stockout_risk_label` is generated by thresholding `stock / daily consumption` in `datasets/build_facility_timeseries.py`, and both stock and consumption are model inputs. Training uses shuffled `train_test_split` on monthly time-series rows. Results therefore leak the target rule and do not measure future-period performance. Metrics do not record a chronological holdout or provenance. The models are trained from synthetic trajectories but are not flagged as synthetic in the metrics or API.

### `frontend/`

Missing: no frontend directory, package manifest, client application, or product views exist. The package lockfile alone does not define a buildable npm project.

## Existing API endpoints

All routes are defined in `backend/app/main.py`:

| Method | Path | Behavior |
|---|---|---|
| GET | `/api/v1/health` | Returns service status and configured app name. |
| GET | `/api/v1/inventory/summary` | Counts unique facilities, districts and medicines, risk buckets, stock units, and latest reporting date from the CSV. |
| GET | `/api/v1/predictions/risk-register` | Returns risk rows; filters by risk, district, and text search; limit is 1–5000. |
| POST | `/api/v1/data/upload-csv` | Validates suffix and required source columns, infers predictions, and returns at most 500 result rows. Does not persist upload. |
| GET | `/api/v1/transfers/recommendations` | Pairs donors and recipients by medicine and estimates possible transfer units. |
| GET | `/api/v1/analytics/trust-metrics` | Returns stored metrics and up to 12 feature importances. |

FastAPI also exposes its generated `/docs`, `/redoc`, and `/openapi.json` routes. No other application endpoints were found.

## Existing views

There are no custom application UI views. Available screens are FastAPI Swagger UI at `/docs` and ReDoc at `/redoc`, plus machine-readable OpenAPI at `/openapi.json`.

## Dependency gaps

- `backend/requirements.txt` includes SQLAlchemy, so the specific claim that SQLAlchemy is missing is **not present**.
- The backend requirements cover its third-party imports (`fastapi`, `uvicorn`, `sqlalchemy`, `pydantic`, `pydantic-settings`, `pandas`, `scikit-learn`, `joblib`, and `python-multipart`).
- Dataset scripts import third-party `numpy` and `pandas`, but there is no dataset-specific requirements file documenting those script dependencies. The root requirements file is absent.
- `package-lock.json` exists without `package.json`, so npm scripts/dependencies and `npm run build` are unavailable. There is no frontend to build.
- The training script's dependency set is only incidentally covered by backend requirements. There is no dedicated ML requirements file.

## Visible code and data issues

- `datasets/build_facility_timeseries.py` randomly assigns every HDX facility district using `np.random.choice`, even where the input could contain district information. It does not set a random seed, so mappings can change between runs.
- In that same generator, labels are computed directly from end-of-month stock divided by daily consumption; both inputs also appear in training features, creating target leakage.
- `datasets/download_and_build_medipredict_data.py` embeds district statistics in source code and labels the resulting source as a fused verified stream, but no source URLs, table references, verification metadata, or provenance document accompany those values. No `is_synthetic` field is present in generated datasets.
- The timeseries generator makes synthetic stock/consumption trajectories, but generated CSV rows and model metrics do not mark or visibly label them as synthetic.
- The download/build script's relative output paths assume it is run from `datasets/`, while the root README only explains backend/model commands.
- Climate download failures are replaced with a hardcoded rainfall value of `4.5`; generated data does not preserve a source/verified flag for this fallback.
- Upload CSV reads the entire request before enforcing the 20 MB size limit, and only checks filename extension rather than MIME/content.
- Upload predictions are computed for all rows but only the first 500 are returned, while aggregate counts cover all rows; result schema has no truncation indicator.
- Risk register and summary reload/read the entire CSV for every request. Empty/malformed/non-numeric CSV values can surface runtime errors.
- Transfer matching uses simple sorted `zip` pairing, can overlook viable pairings, does not validate cross-district or medicine inventory constraints, and assumes 30 days donor buffer / 14 days recipient target.
- `trust-metrics` reports stored holdout metrics without a warning that the source labels are rule-derived and data synthetic.
- Database models are not used to back inventory or predictions; ORM session dependency is attached only to summary but unused.
- Root README claims a pipeline model build despite its leakage and random split, and dataset/ML readmes omit synthetic-data and provenance caveats.
- Several imports are unused (`select`, `Session`/database dependency use is partial, `ConfigDict`, and multiple imports in scripts); this is maintenance debt rather than a runtime failure by itself.
